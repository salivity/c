C Runtime Call Stack and Stack Frames Explained

The C runtime call stack is a dedicated memory region that orchestrates function execution, control flow, and automatic variable storage during program execution. This article explains the architectural role of the call stack in C, breaks down the internal structure of local activation frames (stack frames), and details how the compiler allocates and deallocates these frames using function prologues and epilogues.

The Role of the Call Stack

When a C program runs, its allocated memory is divided into distinct segments: text (machine code), data/BSS (globals and static variables), the heap (dynamic allocations), and the stack.

The call stack operates on a Last-In, First-Out (LIFO) basis. On most modern computer architectures (such as x86 and x86-64), the stack grows downward from higher memory addresses to lower memory addresses. Two primary processor registers manage the active stack boundary:

  • Stack Pointer (e.g., ESP / RSP): Points to the current top (lowest address) of the stack.
  • Frame Pointer / Base Pointer (e.g., EBP / RBP): Holds a fixed reference address for the currently active function frame, enabling stable offset-based access to arguments and local variables.

Structure of an Activation Frame

An activation frame, or stack frame, is a contiguous block of stack memory allocated for a single invocation of a function. Each time a function is called, a new frame is pushed; when the function returns, its frame is popped.

A standard stack frame contains the following components:

  1. Function Arguments: Parameters passed to the function. Under modern 64-bit calling conventions (such as System V AMD64 or Microsoft x64), the first few arguments are passed via CPU registers, with any overflow arguments pushed onto the stack by the caller.
  2. Return Address: The memory address of the instruction directly following the function call in the caller's code. This ensures the CPU knows where to resume execution once the callee finishes.
  3. Saved Frame Pointer: The caller’s base pointer address, stored so the caller's frame can be restored upon return.
  4. Local Variables: Storage for variables declared inside the function that possess automatic storage duration.
  5. Saved Registers: General-purpose registers that the callee must preserve across calls according to the platform Application Binary Interface (ABI).

Frame Management Lifecycle

The lifecycle of an activation frame is automated by compiler-generated machine instructions executed across three phases: the call sequence, the function prologue, and the function epilogue.

1. Function Call Setup

The caller places parameters into designated registers or onto the stack. The caller then issues a call instruction, which pushes the current instruction pointer (return address) onto the stack and jumps to the callee's entry point.

2. The Function Prologue

Immediately upon entering the function, the callee configures its own activation frame:

  • It saves the caller's base pointer: push %rbp
  • It sets the current stack pointer as the new base pointer: mov %rsp, %rbp
  • It reserves memory for local variables by decrementing the stack pointer: sub $N, %rsp (where N is the required byte size aligned to ABI standards).

Once the prologue executes, local variables are accessed using negative offsets from the base pointer (-offset(%rbp)), while stack-passed parameters are accessed using positive offsets (+offset(%rbp)).

3. Execution and Local State

During function execution, all automatic variables live inside this frame. Because access relies on relative offsets, recursive functions seamlessly create distinct activation frames for each invocation without corrupting previous execution states.

4. The Function Epilogue

When the function finishes, the activation frame must be dismantled cleanly:

  • Return values are placed into designated registers (e.g., RAX or EAX).
  • The stack pointer is restored to release local variables: mov %rbp, %rsp
  • The caller's base pointer is restored: pop %rbp
  • The ret instruction pops the return address off the stack and jumps back to the caller.

Practical Implications in C

Understanding stack frame mechanics highlights two critical behavior patterns in C:

  • Automatic Scope: Local variables cease to be valid as soon as the function returns. Returning a pointer to a local stack-allocated variable produces undefined behavior, as that memory space is overwritten by subsequent stack frames.
  • Stack Overflow: Because the runtime stack has a fixed size limit set by the operating system, deep recursion or excessively large local arrays (such as char buffer[10000000];) can exhaust stack memory, causing a crash via a segmentation fault.
