How Rust Interfaces with Legacy C Codebases

Rust interfaces directly with legacy C codebases through its native Foreign Function Interface (FFI). By adhering to the standard C Application Binary Interface (ABI), Rust allows developers to declare and call external C functions, share data structures with predictable memory layouts, and export Rust logic back to C without runtime overhead. This interoperability makes it possible to modernize legacy systems incrementally by replacing or extending C components with memory-safe Rust code while maintaining existing performance levels.

The C Application Binary Interface (ABI)

At the core of Rust’s interoperability is the C ABI. Unlike Rust, which does not have a stabilized ABI, C defines standard conventions for symbol naming, register usage, stack frame organization, and parameter passing. Rust allows developers to match these conventions using the extern "C" keyword. This tells the Rust compiler to generate code that adheres precisely to the target platform’s standard C calling convention.

Declaring External C Functions

To call an existing C function, Rust uses extern "C" blocks. These blocks act as function prototypes, declaring the function signatures that the linker will resolve against compiled C libraries.

#[link(name = "legacy_crypto")]
extern "C" {
    fn hash_data(input: *const u8, length: usize, output: *mut u8) -> i32;
}

The #[link] attribute instructs the Rust compiler to link against the specified dynamic or static C library (e.g., liblegacy_crypto.a or liblegacy_crypto.so).

Handling Types and Memory Layouts

C and Rust have different native data representations, making data layout compatibility critical:

  1. #[repr(C)] Attribute: By default, the Rust compiler can reorder struct fields to optimize memory alignment. Applying #[repr(C)] forces Rust to lay out struct and union fields using the exact same padding, alignment, and ordering rules as the platform's C compiler.
  2. Standard FFI Types: Rust provides C-compatible primitive types via std::ffi (such as c_int, c_char, c_void, and size_t), preventing architecture-specific sizing mismatches.
  3. Strings and Pointers: C strings are null-terminated byte arrays, whereas Rust strings are explicitly sized byte slices (str) or heap allocations (String). Rust provides CString (for passing Rust strings to C) and CStr (for borrowing null-terminated strings from C) to bridge this gap safely.

The Role of unsafe and Safe Wrappers

Because C cannot guarantee memory safety, thread safety, or pointer validity, all foreign functions are treated as inherently unsafe in Rust. Calling an external C function requires an unsafe block:

let result = unsafe {
    hash_data(input_ptr, input_len, output_ptr)
};

Idiomatic integration patterns wrap these raw FFI invocations in safe Rust abstractions. The safe wrapper validates incoming inputs, handles raw pointer dereferences, enforces lifetime bounds, and returns idiomatic Rust types (like Result<T, E>), fully isolating the unsafety to a single boundary layer.

Automating Integration with Bindgen

Writing FFI bindings manually for large legacy codebases is error-prone. The Rust ecosystem solves this using bindgen, a tool that uses libclang to parse C header files (.h) and automatically generate corresponding Rust function declarations, struct definitions, and constants. Integrated into the Rust build script (build.rs), bindgen allows Rust projects to update bindings automatically whenever legacy C headers are modified.

Bidirectional Interoperability

Interoperability works in both directions. Rust functions can be exposed directly to legacy C code by disabling symbol mangling and applying the C calling convention:

#[no_mangle]
pub extern "C" fn rust_process_metric(val: i32) -> i32 {
    val * 2
}

When compiled as a static library (.a) or dynamic library (.so/.dll), the resulting binary can be consumed by the legacy C linker just like any standard C object file, complete with header files generated using tools like cbindgen.
