How C Handles Variadic Functions on the Stack

The C programming language manages variable-length parameter lists (variadic functions) through a combination of calling conventions, pointer arithmetic, and stack memory organization. Because the compiler cannot predict the exact count or types of optional arguments at compile time, it relies on strict runtime conventions where the caller places arguments into memory in a predictable sequence. This article examines how the stack frame is organized, how standard macros like va_start and va_arg traverse memory, and how modern register-based calling conventions adapt these traditional stack mechanisms.

The Foundation: Calling Conventions and Stack Alignment

To make variadic functions possible, C relies heavily on calling conventions that satisfy two main requirements: the caller must clean up the stack, and the position of the first argument must remain predictable.

In traditional 32-bit x86 systems using the cdecl calling convention:

  1. Right-to-Left Push Order: Arguments are evaluated and pushed onto the call stack from right to left.
  2. Caller Cleanup: Because the callee (the called function) does not inherently know how many bytes were pushed, the caller is responsible for adjusting the stack pointer (ESP) after the function returns.
  3. Fixed Anchor Position: Because the rightmost argument is pushed first and the leftmost argument is pushed last, the first named parameter always sits at a known, fixed offset relative to the base pointer (EBP) or stack pointer (ESP).

Under standard architecture rules, stack elements are aligned to word boundaries (4 bytes on 32-bit systems, 8 bytes on 64-bit systems). Types smaller than the architecture's native word size (such as char or short) are widened to int via default argument promotions, guaranteeing predictable memory stepping intervals.

Traditional 32-Bit Stack Layout Mechanics

On a standard 32-bit machine, memory addresses grow downward as the stack grows. When a variadic function such as int printf(const char *format, ...) is invoked:

  1. Optional arguments are pushed onto the stack in reverse order.
  2. The mandatory format pointer is pushed last.
  3. The CALL instruction pushes the return address.
  4. The function prologue pushes the old EBP and allocates local variables.

This creates a contiguous block of arguments in memory where memory addresses increase from the first parameter to the last:

  • [EBP + 0]: Saved Frame Pointer (EBP)
  • [EBP + 4]: Return Address
  • [EBP + 8]: First named argument (format)
  • [EBP + 12]: First variadic argument
  • [EBP + 16]: Second variadic argument
  • [EBP + 20]: Third variadic argument

Because the arguments reside sequentially in memory, any subsequent argument can be accessed using pointer arithmetic anchored to the address of the mandatory named parameter.

How stdarg.h Operates Internally

The <stdarg.h> header provides four macros that formalize stack traversal without requiring inline assembly:

1. va_list

On simple stack-based architectures, va_list is defined simply as a character pointer (typedef char *va_list;). This pointer tracks the current memory address being read on the stack.

2. va_start(ap, last_named_arg)

The va_start macro initializes the va_list pointer. It takes the address of the last known named parameter, adds its aligned size, and assigns the resulting memory address to the pointer:

#define va_start(ap, last_arg) \
    ((ap) = (va_list)&(last_arg) + sizeof(last_arg))

This points the ap pointer directly at the base of the first undeclared argument on the stack.

3. va_arg(ap, type)

The va_arg macro retrieves the value stored at the current pointer location, casts it to the requested data type, and advances the pointer by the size of that type (rounded up to the stack alignment boundary):

#define va_arg(ap, type) \
    (*(type *)((ap += sizeof(type)) - sizeof(type)))

Because the memory layout contains raw bytes with no embedded type metadata, the function must deduce the expected type externally (for example, by parsing %d or %s specifiers in a format string).

4. va_end(ap)

On simple architectures, va_end resets the pointer to NULL to avoid dangling references. On architectures with complex state tracking, it performs necessary cleanup.

Variadic Functions in Modern 64-Bit Architectures

Modern 64-bit calling conventions (such as the System V AMD64 ABI used in Linux/macOS and the Microsoft x64 convention used in Windows) do not pass all arguments on the stack. Instead, the first several integer/pointer arguments are passed via general-purpose registers (e.g., RDI, RSI, RDX, RCX, R8, R9), while floating-point arguments use SIMD registers (XMM0–XMM7).

To preserve the sequential memory traversal model expected by the C standard, the compiler implements a Register Save Area (RSA):

  1. Spilling to the Stack: When a variadic function begins execution, the compiler automatically generates a prologue that dumps the potential argument registers into a contiguous block on the local stack frame.
  2. Complex va_list Structure: In System V AMD64, va_list is not a simple pointer. It is defined as an array of structures containing:
    • gp_offset: Byte offset to the next available general-purpose register in the register save area.
    • fp_offset: Byte offset to the next available floating-point register in the register save area.
    • reg_save_area: Pointer to the base of the register save area on the stack.
    • overflow_arg_area: Pointer to arguments that spilled directly onto the call stack because register capacity was exceeded.
  3. Branching Retrieval: When va_arg is executed, the macro determines whether the requested type should be pulled from the reg_save_area using the register offsets or from the overflow_arg_area on the stack.

Through this spilling process, modern 64-bit C compilers translate register-based calling conventions back into a contiguous stack layout, ensuring that variadic operations behave consistently regardless of underlying hardware differences.
