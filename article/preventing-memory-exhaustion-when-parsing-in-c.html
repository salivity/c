Preventing Memory Exhaustion When Parsing in C

Parsing untrusted or maliciously crafted inputs in C introduces significant risks of memory exhaustion attacks, commonly resulting in denial-of-service (DoS) conditions through unbounded heap allocations or stack overflows. Attackers often exploit parsers using techniques such as decompression bombs, deeply nested payloads, and inflated length headers. Securing a C application against these vectors requires proactive defensive programming, including strict input validation, global memory quotas, recursion limits, and stream-based architectures.

Enforce Strict Bounds on Input-Specified Lengths

Binary formats often encode payload sizes within file or packet headers. A common vulnerability occurs when a parser allocates memory directly based on these untrusted integers without validation (e.g., malloc(header->declared_length)).

  • Cap Allocation Ceilings: Establish a hard maximum size for any single allocation based on application requirements rather than the maximum value supported by the data type.
  • Correlate Size with Available Data: Verify that the declared length does not exceed the remaining bytes in the input buffer or stream. If a header claims an object is 2 GB, but the input stream is only 1 KB, abort the operation immediately.
  • Check for Integer Overflows: Ensure that calculations modifying allocation sizes (such as size * count or length + 1 for null terminators) are checked for integer overflow before calling malloc or calloc.

Implement Memory Budgets and Custom Arenas

Relying exclusively on the system's global malloc makes it difficult to track and restrict how much cumulative memory a particular parsing session consumes.

  • Contextual Memory Quotas: Track cumulative heap usage per connection or parsing context. Increment a counter with every allocation and terminate processing if the aggregate usage exceeds a predefined threshold.
  • Arena Allocators (Region-Based Memory): Allocate a single, fixed-size contiguous buffer (arena) for the parser. Sub-allocate from this pool using an internal offset. If the parser runs out of space in the arena, the input is rejected immediately without risking general system memory starvation, and cleanup requires only resetting a single pointer.

Constrain Recursion Depth and Stack Usage

Recursive-descent parsers processing hierarchical formats like JSON, XML, or ASN.1 are vulnerable to call-stack exhaustion caused by deeply nested structures (e.g., thousands of open brackets).

  • Explicit Depth Counters: Pass an integer tracking the current nesting level through recursive parsing calls. If the depth exceeds a safe limit (e.g., 32 to 128 levels), fail parsing immediately.
  • Iterative Parsing: Replace recursive function calls with an iterative loop and an explicit state stack maintained on the heap, ensuring that stack frame allocation cannot trigger an unrecoverable segmentation fault.

Utilize Stream and Event-Driven Architectures

Loading an entire file into memory before parsing significantly inflates memory footprints and leaves systems vulnerable to memory bloat.

  • Chunked Ingestion: Read and process data in small, fixed-size buffers (e.g., 4 KB to 64 KB).
  • Pull/Token Parsers: Implement SAX-style or token-stream parsing instead of building full in-memory Document Object Models (DOM). Emit events as tokens are encountered and discard parsed segments immediately once processed.

Guard Against Data Amplification Attacks

Attacks such as "billion laughs" or decompression bombs provide a small input that expands exponentially when parsed or decompressed.

  • Monitor Expansion Ratios: When decompressing or expanding entities, calculate the ratio of decompressed bytes to compressed input bytes. If the expansion ratio exceeds an acceptable threshold (e.g., 10:1 or 100:1 depending on format), immediately abort.
  • Limit Dynamic Expansion: Disable dynamic entity expansion entirely if the format allows it, or substitute entities only once rather than recursively resolving nested references.

Handle Allocation Failures Gracefully

Always check the return values of malloc, calloc, and realloc. If an allocation fails due to memory constraints:

  • Release all previously allocated resources linked to the current context to avoid memory leaks.
  • Return an explicit error code to the caller.
  • Avoid calling abort() or exit() inside parsing libraries so the host application can maintain stability and handle the event securely.
